# ADR-003：编辑器内核选型

**状态**：✅ 已定
**日期**：2026-08-17

---

## 背景

需求要求编辑区「完全参考 note-gen」，同时要兼容 `md` `txt` `sql` `json` `yaml` `yml` `xml` 七类格式。而两个参考项目用的是**完全不同**的编辑器：

| 项目 | 编辑器 | 模式 |
|---|---|---|
| **note-gen** | **TipTap 3（WYSIWYG）+ CodeMirror 6（源码）** | 严格二选一，无分栏预览、无即时渲染 |
| **TMD** | **Vditor**（`mode: 'ir'`） | 即时渲染（Typora 式），单一模式 |

note-gen 的实测细节：

- 类型 `EditorViewMode = 'visual' \| 'source'`，默认 `visual`
- 全仓 grep `splitView|side-by-side|livePreview|preview-pane` = **0 命中** → 确认无分栏预览
- 序列化唯一依赖 `@tiptap/markdown`（TipTap 官方，内部基于 marked）
- 入：`editor.commands.setContent(md, { contentType: 'markdown' })`；出：`editor.getMarkdown()`，debounce 500ms
- 解析失败时置 `markdownParseError` 并**强制回落 source 模式**
- CM6 是**裸用**（无 React wrapper），手写 `new EditorView` / `EditorState.create`，5 个 `Compartment` 做热重配
- 切模式时保存/恢复选区 + 滚动位置

TMD 的实测细节：

- Vditor 自托管在 `public/vditor/dist/`，**528 个文件手工拷进仓库并提交**，无同步脚本，升级要手动重拷
- Vditor 层面只切「明暗」两档（`theme: 'dark' | 'classic'`），8 套配色 100% 靠 `[data-theme]` CSS 变量 + `!important` 覆盖
- `contentTheme` / `codeTheme` 参数**从未传入**，永远停留在默认 `light` / `github`
- 字体族与字号**不可调**（沿用 Vditor 自带 `.vditor-reset`）

## 决策

**采用 note-gen 的方案：TipTap 3（visual）+ CodeMirror 6（source），严格二选一切换。**

具体：

| 用途 | 内核 |
|---|---|
| Markdown · visual 模式 | TipTap 3 / ProseMirror |
| Markdown · source 模式 | CodeMirror 6 + `@codemirror/lang-markdown` |
| `.txt` `.sql` `.json` `.yaml` `.yml` `.xml` 等 | CodeMirror 6 + 对应语言包 |
| `.excalidraw` | Excalidraw（见 [ADR-008](ADR-008-画板引擎与文件格式.md)） |

版本用 TipTap **3.30.1** 或更新（note-gen 的 3.19.0 已过时）。

### 关键理由：CM6 是刚需，不是可选项

需求要求 `.sql` / `.json` / `.yaml` / `.xml` 有真正的语法高亮。这件事**只有 CM6 能做**（Vditor 做不了，TipTap 也做不了）。

既然 CM6 必装，那么：

- 选 TipTap + CM6 → **两个内核，各司其职**，source 模式与代码文件编辑复用同一套 CM6 配置、同一套语法高亮主题、同一套查找替换
- 选 Vditor + CM6 → **三个内核**（Vditor 的 IR 编辑 + Vditor 内部的 CodeMirror + 我们的 CM6），主题要适配三套，体积更大，收益为零

### 用户喜欢的 TMD 主题不受影响

TMD 的配色是纯 CSS 变量（`--code-inline-bg`、`--editor-text` 等）。这些变量**与编辑器无关**，只需把消费端的选择器从 Vditor 的 `.vditor-reset` / `.hljs-*` 改写到 TipTap 的 `.ProseMirror` / `.hljs-*` 与 CM6 的 `HighlightStyle`。色值 1:1 转移。见 [ADR-009](ADR-009-主题Token体系与无障碍基线.md)。

## 被否方案

### Vditor（TMD 的选择）

否决理由：

1. **自托管 528 个文件进仓库，无升级路径。** TMD 就是这么干的，升级 Vditor 要手动重拷整个 dist。
2. **主题能力受限。** Vditor 只暴露明暗两档，一切细粒度配色都要靠 `!important` 硬覆盖它的内置 CSS。TMD 的 `vditor-styles.css` 有 37.7 KB 几乎全是覆盖规则。
3. **不解决代码文件需求。** 仍需另装 CM6。
4. **与「完全参考 note-gen」的要求相悖。**
5. Vditor 内部也捆了一个 CodeMirror 用于代码块编辑，与我们的 CM6 重复。

### 分栏预览（编辑区 + 实时预览左右对照）

否决：note-gen 明确没有（grep 零命中），需求也没要求。双模式已覆盖「想看原文」的场景，且分栏预览需要维护滚动同步这个长期麻烦。记为 [OUT-109](../01-需求规格说明.md)。

### Milkdown / Monaco / Tiptap 2

- Milkdown：也是 ProseMirror 系，但生态与文档不如 TipTap，且 note-gen 没用
- Monaco：体积大（~5MB），为 IDE 场景设计，对「记事本替代品」过重；CM6 更轻且模块化
- TipTap 2：3.x 已稳定且 note-gen 用的是 3.x

## 代价

### 1. Markdown 序列化往返有损，且这是最容易伤到用户信任的地方

`@tiptap/markdown` 的序列化会规范化空格、列表标记、强调符号。**打开一个文件、切一次模式，文件就可能被标记为已修改。**

用户看到的是「我什么都没做，软件说我改了文件」——这在「记事本替代品」定位下是严重的信任伤害。

**对策**（已写进 [领域模型](../03-领域模型.md) 不变式 I-13/I-14）：

- 进入 visual 模式时记录**规范化后的基线文本**
- 脏判定与**基线**比较，不与磁盘原文比较
- `Ctrl+S` 时若内容等于基线则**跳过写盘**
- 往返测试必须覆盖：非标准 HTML 块、混合缩进列表、行尾空格、setext 标题、引用嵌套、表格对齐符

### 2. 两个内核的行为要对齐

查找替换、快捷键、光标位置显示、字数统计在两个内核里是两套实现，需要刻意对齐 UI 与快捷键。

### 3. 光标位置在模式切换时需要坐标映射

PM 的 position 与字符偏移不是一回事（PM 每个节点边界占 1）。切换时要做映射，映射不精确会导致光标跳到邻近位置。可接受，但需要测试覆盖。

### 4. TipTap 的 drag-handle 强制 `dragDropEnabled: false`

见 [ADR-014](ADR-014-拖放机制取舍.md)。这是选 TipTap 带来的连带约束。

## 什么情况下该重新考虑

- `@tiptap/markdown` 的序列化保真度被证明无法接受（往返测试大面积失败）
- 需要分栏预览
