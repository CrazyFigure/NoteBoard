# ADR-010：状态管理与跨窗口同步

**状态**：✅ 已定
**日期**：2026-08-17

---

## 背景

note-gen 是**单窗口**应用：`tauri.conf.json` 的 `app.windows` 只声明一个 `main`，`window.rs` 全文只有 `app.get_webview_window("main")`，无 `WindowBuilder`。它的 tab 状态存在**全局单例** `store.json` 里（`src/stores/article.ts` 128 KB，`OpenTabInfo` + `addTab` 上限 `slice(-10)`）。

NoteBoard 是多窗口。直接照抄 note-gen 的模型会立刻坏掉：两个窗口会读写同一份 tab 列表。

调研结论中最尖锐的一句：

> 前两块（多窗口、跨窗口 tab 拖拽）会反过来要求你把 note-gen 那套「全局单例 tab 状态存 store.json」的模型从一开始就改成 per-window 分片 —— **这是架构决策，越晚改越贵。**

同时 Tauri v2 有两个必须知道的事实：

1. **`emit` 的语义与 v1 相反。** v2 里在 `Window` / `WebviewWindow` 实例上调 `.emit()` **也是广播**，不会自动限定到该窗口。定向必须显式 `emit_to(label, ...)`。
2. **新窗口在 `build()` 返回时还没执行任何 JS。** 此时 `emit` 出去的事件没有监听者，直接丢失。

## 决策

### 1. 状态分片：per-window store + Rust 注册表

| 数据 | 位置 | 理由 |
|---|---|---|
| tab 列表、激活 tab | **前端，每窗口一份** | 纯 UI 状态，窗口间无关 |
| 文档内容、撤销栈、光标、滚动 | **前端，每窗口一份** | 编辑器内核持有，无法序列化 |
| 资源管理器根、展开状态 | **前端，每窗口一份** | 纯 UI 状态 |
| 面板可见性与宽度 | **前端，每窗口一份**（Rust 落盘） | |
| **「哪些文件已打开、在哪个窗口」** | **Rust `AppState.documents`** | 跨窗口唯一性只能在共享层裁决 |
| **窗口列表与 label** | **Rust `AppState.windows`** | 窗口是 OS 资源 |
| **主题与排版设置** | **前端全局单例 + Rust 落盘 + 广播** | 必须所有窗口一致（FR-1004） |

### 2. Store 拆分（前端）

```ts
windowStore     tabs / activeTabId
documentStore   documents Map + 脏态 + ViewState
explorerStore   root / expanded / revealed / children
layoutStore     面板可见性与宽度
settingsStore   主题 + 排版（跨窗口同步的唯一 store）
```

**`windowStore` 与 `documentStore` 必须拆开。** 理由：文档内容变更（每次按键）绝不能引起 tab 栏重渲染。拆 store 是最省事的隔离手段。

### 3. 编辑器内容不进 store 当受控值

**编辑器内核持有内容的权威副本**（TipTap 的 `editor.state.doc`、CM6 的 `EditorState`、Excalidraw 的 scene）。`documentStore.content` 是**防抖后的镜像**，用途只有两个：保存时取值、切 tab 卸载编辑器时保底。

**禁止把 store 的 content 当受控值回灌给编辑器** —— 会造成光标跳动与输入卡顿。

同步节奏：

| 内核 | 回调 | → store | → 磁盘 |
|---|---|---|---|
| TipTap | `onUpdate` | 500ms 防抖 | 800ms 防抖（auto） |
| CM6 | `updateListener` | 300ms 防抖 | 仅 `Ctrl+S` |
| Excalidraw | `onChange` | 300ms 防抖 | 800ms 防抖（auto） |

### 4. Rust 侧共享 state

```rust
use tauri::Manager;

app.manage(Mutex::new(AppState::default()));    // 挂在 App 上，天然跨全部窗口共享，无需 Arc

#[tauri::command]
async fn open_in_new_window(state: tauri::State<'_, Mutex<AppState>>) { ... }
```

**用 `std::sync::Mutex`**，不用 async mutex（官方 state-management 指南的默认示范，且跨 `await` 持 std Mutex 会有编译/panic 风险 —— 所以持锁范围必须短，不跨 await）。`RwLock` 只在实测出读竞争瓶颈时再换。

非 command 处取 state（如 single-instance 回调，参数是 `&AppHandle`）：

```rust
let state = app.state::<Mutex<AppState>>();          // 未注册会 panic
// 或 app.try_state::<Mutex<AppState>>()             // 安全版
```

### 5. 事件投递：定向用 `emit_to`，广播用 `emit`

| 事件 | 投递 |
|---|---|
| `nb://open-files` | `emit_to(label)` |
| `nb://external-change` | `emit_to(owner)` |
| `nb://explorer-refresh` / `-rescan` | `emit_to(label)` |
| `nb://focus-tab` | `emit_to(label)` |
| **`nb://settings-changed`** | **`emit` 广播** |
| **`nb://before-quit`** | **`emit` 广播** |

> 🔴 **代码审查必查项**：任何 `.emit(` 调用都要确认是**故意要广播**。v2 里 `window.emit()` 也是广播，这是最容易写错的地方。

### 6. 新窗口交接：拉取模型（Pull Handoff）

**不用「建窗后 emit 事件」。** 改为：

```
① 源窗口/单实例回调              ② Rust                      ③ 新窗口
                                    │
   ─── invoke(create_window) ──────►│
       (含 WindowIntent)            ├─ intents[label] = intent
                                    ├─ thread::spawn(build())  🔴 必须切线程
                                    │                            ├─ 前端挂载完成
                                    │◄─── invoke(window_ready) ──┤
                                    ├─ intents.remove(label) ───►│ 拿到 intent
                                    │                            ├─ 恢复内容与 ViewState
```

**`window_ready` 把「握手」与「取意图」合并为一个命令** —— 少一次往返，且天然消除「已 ready 但还没取意图」的中间态。

**新窗口是时序的主动方**，不存在竞态。

### 7. 对账机制（保障不变式 X-6）

Rust 的 `documents` 与各窗口 `documentStore` 的并集必须一致，否则出现「幽灵文档」：Rust 认为文件开着，界面上找不到，用户从此打不开那个文件。

保障手段：

- 前端每次增删 Document 都 `invoke('register_document')` / `invoke('unregister_document')`
- Rust 提供 `reconcile_documents(label, keys[])`
- 前端在**窗口 ready 时**与**每 30 秒**各调一次，发现不一致**以前端为准**修正 Rust
- 窗口关闭时（`tauri://close-requested` 流程内）显式注销该窗口名下全部文档

### 8. 设置的跨窗口一致性

- **写入只允许通过 `invoke('save_settings')`**，本地先乐观更新
- 收到 `nb://settings-changed` 广播时**全量替换**（不做字段级合并，避免顺序问题）
- 广播的发起窗口也会收到自己的广播，用 `revision`（单调递增）去重

## 被否方案

### 照抄 note-gen：全局单例 tab 状态存 store.json

否决：多窗口下立刻坏掉。两个窗口读写同一份 tab 列表，互相覆盖。

### 全部状态放 Rust，前端只做渲染

否决：撤销栈、光标位置、ProseMirror 文档树无法序列化传输；每次按键往返 IPC 会毁掉输入延迟（NFR-104 要求 p95 ≤ 32ms）。

### 用 `localStorage` / `BroadcastChannel` 做跨窗口同步

否决：Tauri 的每个 `WebviewWindow` 是独立的浏览上下文，同源但 `BroadcastChannel` 在 WebView2 多窗口间的行为**未验证**且无官方契约。Rust 的 `emit` 广播是有文档保证的路径，不引入不确定性。

### 建窗后 `emit` 投递意图

否决：新窗口在 `build()` 返回时还没执行 JS，事件必然丢失。这是 Tauri 多窗口最常见的 bug。

（若非要走这条路，需要「新窗口 ready 后回告 → Rust 再 emit」的握手，那还不如直接让新窗口来拉。）

### 单一 store（不拆 window/document）

否决：文档内容变更会引起 tab 栏重渲染。1MB 文档里每次按键都重渲染整个 tab 栏，直接违反 NFR-104。

## 代价

1. **多了一层对账机制。** 是为了防「幽灵文档」这个体验极差的故障。对账逻辑本身要有测试。
2. **窗口崩溃时 Rust 侧可能残留 `DocumentRecord`。** 靠 `tauri://close-requested` 正常路径清理 + 定期对账兜底。非正常退出（进程被杀）时残留会随进程消失，无害。
3. **未保存内容跨窗口迁移必须由前端传输**（Rust 不知道内容）。这条约束贯穿 FR-606 的实现，也是不变式 I-10 存在的原因。
4. **`Mutex` 持锁范围必须短且不跨 await。** 需要在 code review 中盯。

## 什么情况下该重新考虑

- 实测出 `Mutex` 竞争成为瓶颈（换 `RwLock` 或分片锁）
- 对账机制被证明不够，出现难以复现的幽灵文档
