# ADR-001：桌面框架选型

**状态**：✅ 已定
**日期**：2026-08-17

---

## 背景

NoteBoard 是 Windows 桌面应用，候选框架是 Tauri v2 与 Electron。做选择时，最初认为决定性因素是「tab 跨窗口拖拽合并」这条需求——因为那是两个框架能力差异最大的地方。

调研结论（当时）：

| 维度 | Tauri v2 | Electron |
|---|---|---|
| 跨窗口 HTML5 DnD 传数据 | ❌ 官方确认不做（[tauri#15138](https://github.com/tauri-apps/tauri/issues/15138) closed as not planned、[#9976](https://github.com/tauri-apps/tauri/issues/9976)） | ✅ VSCode 生产验证（自定义 MIME `CodeEditors`） |
| 搬运活 renderer | `reparent` 存在但标记 `unstable` | ✅ 官方测试验证（≥31.x），但 Windows 有 hidden→visible 抖动 |
| 可照抄的生产源码 | Folia PR#52（1808 行，6★） | VSCode（MIT）+ Obsidian 先例 |
| 自绘 tab 栏 × 指针事件 | `data-tauri-drag-region` 仅作用于直接标注元素，语义精确 | 🔴 [electron#28057](https://github.com/electron/electron/issues/28057) 维护者已确认的 **Windows 专属** bug：draggable region 之上的 view 吞掉所有点击 |
| 安装包 / 单窗口内存 | ~8 MB / ~60 MB | ~90–244 MB / ~130 MB |

后来**这条需求被取消了**（见 [ADR-006](ADR-006-窗口与Tab模型.md)），于是唯一让 Electron 有竞争力的理由消失。

## 决策

**采用 Tauri v2**（crate `2.11.5`，`@tauri-apps/api 2.11.1`，`@tauri-apps/cli 2.11.4`，MSRV 1.77.2）。

理由按权重：

1. **跨窗口拖拽需求取消后，Electron 的两处真实优势（跨窗口 DnD 传数据、搬运活 renderer）对本项目完全无用。** NoteBoard 所有 tab 都是同一份应用代码渲染不同文档，不需要在 tab 里嵌任意第三方网页——那是唯一真正需要 `WebContentsView` 的场景。
2. **多窗口是 NoteBoard 的核心形态。** 用户要「像记事本一样随手开十几个窗口」，Tauri 的单 Rust 进程 + 共享 WebView2 浏览器进程结构在这里有结构性优势，且用户能直接感知（内存占用、启动速度）。
3. **`data-tauri-drag-region` 的语义比 Electron 的 `app-region: drag` 干净。** 官方文档明确：「只作用于直接标注的元素」，不继承给子元素。自绘 tab 栏时只给空白区加这个属性即可，tab 本身不受影响。Electron 的 #28057 恰好击中「自绘 tab 栏 + view」这个组合，且是 Windows 独有、至今 OPEN。
4. **参考项目同栈。** note-gen 与 TMD 都是 Tauri v2 + React，两者的 Tauri 侧配置（fileAssociations、single-instance、多窗口、自绘标题栏）都是可直接对照的生产实现。
5. **安装包 ≤ 30 MB 的目标（NFR-110）Electron 达不到。**

## 被否方案

### Electron 43.x

否决理由：上述 1–5 的镜像。补充两条：

- **note-gen 的 Tauri 后端调用（fs / dialog / 插件）需要全部改写成 Electron IPC**，而移植 note-gen 代码正是 GPL-3.0 换来的核心收益（[ADR-002](ADR-002-开源协议与代码复用边界.md)）。换 Electron 会把这份收益折损相当一部分。
- Chromium 版本锁定这个 Electron 优势对本项目不重要——我们不依赖前沿 Web API。

### Tauri v1

否决：v2 才有 capabilities 权限模型、多窗口 API 完善、插件生态已迁移。v1 已停止新功能。

### 原生（WinUI 3 / WPF / Qt）

否决：Markdown 所见即所得编辑器（TipTap/ProseMirror）与 Excalidraw 都是 Web 生态资产，原生栈要么全部自研，要么仍要嵌 WebView。没有收益。

## 代价

1. **依赖 WebView2 Runtime**，版本不受我们控制。用户机器上的 WebView2 版本差异可能带来渲染差异。采用 `downloadBootstrapper`（默认）应对缺失。
2. **需要 Rust 能力。** 文件 I/O、监听、窗口管理、编码处理都在 Rust 侧。
3. **Windows 建窗死锁**（wry#583）：`WebviewWindowBuilder::build()` 在同步 command 或事件回调中调用会挂死。所有建窗路径必须走 `async fn` 或 `std::thread::spawn`。**single-instance 回调里建窗尤其危险**——它运行在 `WM_COPYDATA` 同步窗口过程里，同时命中两个条件。这条已写进 [领域模型](../03-领域模型.md) 与 [路线图](../09-开发路线图.md) 的实现红线。
4. **运行时建的窗口默认无 IPC 权限**。capabilities 的 `windows` 数组必须用 `nb-*` 通配匹配，且需显式加 `core:webview:allow-create-webview-window`（`core:webview:default` 不含它）。官方原文：「If a webview or its window is not matching any capability then it has no access to the IPC layer at all.」
5. **`dragDropEnabled` 与 WebView 内 HTML5 拖拽是硬二选一**（见 [ADR-014](ADR-014-拖放机制取舍.md)）。这是 Tauri/wry 在 Windows 上的特有约束，Electron 没有。

## 什么情况下该重新考虑

- tab 里需要嵌**任意第三方网页**（必须搬运活 renderer）
- 需要严格锁定 Chromium 版本
- WebView2 在目标用户群体中的缺失率被证明过高
