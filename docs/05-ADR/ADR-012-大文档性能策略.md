# ADR-012：大文档性能策略

**状态**：✅ 已定
**日期**：2026-08-17

---

## 背景

NoteBoard 要当记事本替代品，用户会拿它打开日志、导出的 SQL、大 JSON。ProseMirror 在大文档上会退化得很难看：一篇 5 MB 的 Markdown 直接进 TipTap，建 AST + 建 DOM 会卡住主线程几十秒。

note-gen 有一套完整的四层机制，实测细节：

**① 阈值判定**（`large-markdown.ts`）
```ts
LARGE_MARKDOWN_CHARACTER_THRESHOLD  = 200_000
LARGE_MARKDOWN_LINE_THRESHOLD       = 4_000
LARGE_MARKDOWN_HEAVY_NODE_THRESHOLD = 160
```
单趟 `charCodeAt` 扫描（不建 AST）：数换行 + 数「重节点标记」（`![` 图片、` ``` ` / `~~~` 围栏、`$$`、`\(` `\[`、`<img`），任一阈值命中即提前 return。命中后默认开 source 模式 + 显示横幅让用户显式「打开可视化」。

**② 视口懒渲染**（`viewport-activation.ts` + `viewport-lowlight-plugin.ts`）
- `IntersectionObserver`，`rootMargin: '800px 0px'`
- **observer 按 root 复用**（`WeakMap<Element, ObserverEntry>` + document 级 fallback），不是每个元素一个
- **一次性触发**：命中后立即 `callbacks.delete(target)` + `observer.unobserve(target)`
- lowlight 插件只对视口 **±2000 position** 内的代码块产 `Decoration.inline`；rAF 批处理 + `setMeta('addToHistory', false)`；对 `lastDoc`/`lastRange` 记忆化；**单块 > 20,000 字符跳过**，`highlightAuto` 仅对 ≤ 5,000 字符的块

**③ 分段虚拟滚动**（`section-document.ts` + `sectioned-markdown-editor.tsx`）
```ts
DEFAULT_SECTION_TARGET_CHARACTERS = 24_000
DEFAULT_SECTION_MAX_CHARACTERS    = 64_000
```
- 用 `markdown-it` 只做块级 token 解析求安全边界，**只在完整块边界切**（不切开代码围栏/表格/frontmatter）
- `@tanstack/react-virtual` 的 `useVirtualizer`，`overscan: 2`，配 `defaultRangeExtractor` 保证激活段始终在渲染范围内
- **同时只有 1 个段是真 TipTap 实例**，其余段用 `markdown-it` 渲染成只读 HTML

**④ Web Worker 分段**（`section-document-worker.ts`）
- `new Worker(new URL('./section-document-worker.ts', import.meta.url), { type: 'module' })`
- worker 内先补 `globalThis.isSpace` polyfill（markdown-it 在打包器下的坑），再 `await import('./section-document')`
- **回传时把 `source` 抹成 `''`**，避免把整个大文件字符串拷回主线程 —— 调用方本来就持有 source

用户被问「全部照做还是先做前两层」时，明确选择**四层全上**。

## 决策

**四层全部实现，阈值与关键魔法值沿用 note-gen 的实测值。**

| 层 | 需求编号 | 实现 |
|---|---|---|
| ① 阈值回落 | NFR-201 | 200,000 字符 / 4,000 行 / 160 重节点，单趟扫描提前 return |
| ② 视口懒渲染 | NFR-202 | `IntersectionObserver` `rootMargin: 800px`，observer 按 root 复用，一次性触发 |
| ③ 分段虚拟滚动 | NFR-203 | 24,000 目标 / 64,000 上限，块边界切分，`@tanstack/react-virtual` `overscan: 2`，同时 1 个真实例 |
| ④ Worker 分段 | NFR-204 | Worker 内 `markdown-it` 块解析，回传抹掉 `source` |

### 沿用而不重新推导魔法值

这些数字是 note-gen 踩坑得出的经验值，没有理由重新试：

| 值 | 作用 |
|---|---|
| `rootMargin: 800px` | 提前渲染距离，太小会看到空白，太大失去懒渲染意义 |
| `±2000 position` | lowlight 裁剪范围 |
| `overscan: 2` | 虚拟滚动预渲染段数 |
| `24,000 / 64,000` | 段目标/上限字符数 |
| `20,000` | 单代码块跳过高亮的阈值 |
| `5,000` | `highlightAuto` 的上限 |
| KaTeX LRU 200 | 公式渲染缓存条目数 |

**但要在文档里标注它们是经验值而非推导值**，将来调整时知道可以调。

### 三处必须自己加的东西

note-gen 的机制服务单窗口单文档，我们要补：

1. **`largeDoc` 判定结果存进 `Document`**（`LargeDocVerdict`），切 tab 回来不重算。
2. **Worker 按窗口复用一个实例**，不是每个大文档一个 Worker。
3. **Mermaid 的全局串行队列要跨 tab 生效**（`mermaid.render()` 并发调用会互相污染内部状态）。note-gen 单窗口时队列是模块级单例，我们仍是模块级（每窗口一个 webview = 一个模块实例），语义正确。

### 代码类文件不需要这套机制

CM6 **自带**视口虚拟化与增量语法解析，打开 100 MB 的 JSON 也不会卡。所以：

- 四层机制**只服务 Markdown 的 visual 模式**
- `kind: 'code'` 的文件直接给 CM6，无阈值、无分段
- Markdown 的 source 模式也走 CM6，所以「阈值回落到 source 模式」本身就是回落到一个天然抗大文件的内核 —— **这是第①层为什么有效的根本原因**

### 打开超大文件的前置确认（FR-113）

超过 **50 MB** 时，在读盘**之前**弹确认框（继续 / 取消 / 以只读源码模式打开）。

这一层在四层机制之外、之前 —— 因为四层机制都在「内容已经读进内存」之后才起作用，而读 500 MB 文件进内存本身就是问题。

## 被否方案

### 只做前两层（阈值回落 + 视口懒渲染）

我原本推荐这个：覆盖绝大多数真实场景，省 5–8 天。

**用户选择四层全上，且这个选择是合理的**：第③④层解决的是「用户明确要在大文档里用可视化编辑」的场景。只做前两层的话，那个场景下用户只能用源码模式——对一篇 30 万字的书稿，这个限制是真实的痛点。

### 不做任何优化，靠 ProseMirror 自己

否决：5 MB Markdown 直接进 TipTap 会卡死几十秒。这是必然发生的，不是极端情况。

### 用 CM6 完全替代 TipTap 处理大文档

这实际上就是第①层。只做这个的问题是：用户在大文档里彻底失去可视化编辑。

### 自己写虚拟滚动而不用 `@tanstack/react-virtual`

否决：没有理由。`defaultRangeExtractor` 的定制点（保证激活段始终渲染）正是我们需要的能力。

## 代价

1. **这是整个项目最复杂的一块。** 估工 5–8 天，且 bug 密度高。
   - 涉及：Worker 通信、块边界解析正确性、虚拟滚动与真实编辑器实例的协调、活动段编辑后回写原文并重算边界。
2. **分段模式下的编辑体验与非分段模式有差异**：跨段选择、跨段查找替换、跨段撤销都需要特殊处理。
   - **明确的范围限制**：分段模式下**不支持跨段选择与跨段拖拽块**。查找替换需要跨段搜索但一次只在活动段内替换。这些限制要在 UI 上说明（横幅提示「分段编辑模式」）。
3. **大纲在分段模式下需要从原文而非 PM doc 提取**（因为只有活动段有 PM doc）。这是一处例外，违反了「大纲从编辑器文档树提取」的常规做法，需要单独实现路径。
4. **测试成本高。** 需要构造 200KB / 1MB / 5MB / 50MB 的测试样本，且要覆盖「块边界恰好落在代码围栏中间」这类边界。

## 什么情况下该重新考虑

- 第③④层实现后实测收益不明显（用户很少在大文档里用可视化编辑）
- ProseMirror 上游解决了大文档性能问题
