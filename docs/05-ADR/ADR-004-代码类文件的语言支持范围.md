# ADR-004：代码类文件的语言支持范围

**状态**：✅ 已定
**日期**：2026-08-17

---

## 背景

需求：「文本格式至少需要兼容 md、txt、sql、json、yaml、yml、xml」。

note-gen 在这件事上是**负面参考**。实测：

```
MARKDOWN_EXTENSIONS（src/app/core/main/editor/editor-layout.tsx:50-55，37 项）：
md, txt, markdown, py, js, ts, jsx, tsx, css, scss, less, html, xml, json,
yaml, yml, sh, bash, java, c, cpp, h, go, rs, sql, rb, php, vue, svelte,
astro, toml, ini, conf, cfg, gitignore, env, example, template
```

这 37 种**全部路由到 Markdown 编辑器**。后果：

- `.sql` / `.json` 在 visual 模式下会被 Markdown 解析 + 序列化**往返**，内容可能被改写
- CM6 侧**只装了 `@codemirror/lang-markdown`**（grep 确认无任何其他 `@codemirror/lang-*`，也无 `@codemirror/language-data`），`source-markdown-editor.tsx:190` 硬编码 `markdown()` 无参数
- 结果：`.sql` 在源码模式下得到的是 **Markdown 高亮**
- 且没有任何按扩展名强制 source 模式的逻辑

note-gen 内部还有三套互不一致的白名单：`MARKDOWN_EXTENSIONS`（37 项）、`OPENABLE_EXTENSIONS`（只有 `md`/`markdown`，用于 OS 文件关联）、索引层只认 `.md`。文件树是裸 `readDir`，所以非 md 文件会显示且可点。

## 决策

**只为点名的 5 种语言提供真正的语法高亮，各自动态 `import()` 加载。**

| 语言 | 扩展名 | CM6 包 | 附加能力 |
|---|---|---|---|
| Markdown | `.md` `.markdown` | `@codemirror/lang-markdown` | source 模式用 |
| SQL | `.sql` | `@codemirror/lang-sql` | — |
| JSON | `.json` | `@codemirror/lang-json` | **语法错误提示 + 折叠 + 格式化** |
| YAML | `.yaml` `.yml` | `@codemirror/lang-yaml` | **语法错误提示 + 折叠** |
| XML | `.xml` | `@codemirror/lang-xml` | **标签匹配 + 折叠 + 格式化** |

**其余文本类扩展名**（`.txt` `.log` `.ini` `.conf` `.cfg` `.env` 及表外的未知扩展名）→ `plaintext`：CM6 无语言支持，但仍有行号、当前行高亮、查找替换、软换行。**能正常读写，不会损坏内容。**

**明确不装 `@codemirror/language-data`** —— 它会把全部语言包拉进依赖图。

### 单一真相源

扩展名映射只在一处定义：`src/core/docKind.ts` 的 `KIND_BY_EXT`。Rust 侧从同一份 JSON 生成，避免 note-gen 那种三套白名单互不一致的问题。测试断言两侧一致。

### 严格按 DocumentKind 分派

```
.md / .markdown  → kind: 'markdown' → 双模式（TipTap / CM6）
.sql .json .yaml .yml .xml .txt … → kind: 'code' → CM6，永不进 Markdown 编辑器
.excalidraw      → kind: 'board'
二进制           → kind: 'unsupported' → 文件信息页，不渲染内容
```

**`kind: 'code'` 的文件绝不会被 Markdown 解析。** 这是与 note-gen 最重要的分歧。

## 被否方案

### 跟 note-gen 一样，全部走 Markdown 编辑器

否决：会改写 `.sql` / `.json` 的内容。对「记事本替代品」是致命缺陷 —— 用户拿它改生产环境的配置文件，结果文件被 Markdown 序列化规范化了。

### 装 `@codemirror/language-data`，支持全部语言

否决理由：

1. 需求只点名了 6 种格式，超出部分是**范围蔓延**
2. `language-data` 的动态加载虽然是按需的，但它引入大量间接依赖，且需要为每种语言验证高亮 token 与我们的 `--hljs-*` 主题映射是否合理
3. 用户在被问到时明确选择了「只做点名的六种」

**但**：架构上留好扩展点。`features/editor-code/languages.ts` 是一个 `Record<LanguageId, () => Promise<LanguageSupport>>`，加一种语言只需加一行 + 一个动态 import + 在 `KIND_BY_EXT` 里注册。将来要扩不需要重构。

### 用 highlight.js 给 CM6 做高亮（复用 lowlight）

否决：CM6 有自己的 Lezer 增量解析体系，硬塞 highlight.js 会失去增量解析、折叠、括号匹配、lint 这些依赖语法树的能力。**但两者的颜色统一到同一套 `--hljs-*` 变量** —— 见 [ADR-009](ADR-009-主题Token体系与无障碍基线.md)。

## 代价

1. **打开 `.py` / `.js` / `.ts` 等常见代码文件时没有高亮。** 用户如果期望它当通用代码编辑器会失望。缓解：状态栏显示「纯文本」，让期望明确。
2. **五个语言包各自动态加载**，首次打开某类型文件有一次约 30–120 KB 的加载延迟（本地文件，实测应在 50ms 内）。
3. `KIND_BY_EXT` 需要前后端两侧同步，有出错风险。用测试锁住。

## 什么情况下该重新考虑

- 用户实际使用中频繁打开其他语言的文件
- 打开 `.py` / `.js` 无高亮成为主要抱怨点

扩展成本很低（每种语言约 10 行代码 + 一次 token 配色核对），所以这条决定是**容易反转**的，不必现在过度设计。
