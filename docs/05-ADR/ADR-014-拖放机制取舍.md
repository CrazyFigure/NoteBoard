# ADR-014：拖放机制取舍

**状态**：✅ 已定
**日期**：2026-08-17

---

## 背景

NoteBoard 需要三件涉及拖放的事：

| | 需求 | 编号 |
|---|---|---|
| **(a)** | TipTap 段落左侧「⠿」块把手拖动排序 | [FR-311](../01-需求规格说明.md) P0，用户明确要求 |
| **(b)** | tab 栏内同窗口拖拽排序 | [FR-604](../01-需求规格说明.md) P1 |
| **(c)** | 从资源管理器把文件拖进窗口打开 | [FR-104](../01-需求规格说明.md) 原 P1 |

调研中出现三份看似矛盾的证据：

- wry rustdoc 说 `dragDropEnabled: true` 会「disable the HTML Drag and Drop APIs like `draggable=true`」
- **note-gen** 配的是 `dragDropEnabled: **false**`，而它**有** TipTap drag-handle
- **TMD** 配的是 `dragDropEnabled: **true**`，而它**没有** drag-handle

## 这三份证据其实完全一致

源码层核实（`wry/src/webview2/drag_drop.rs`）：

```rust
let drag_drop_target: IDropTarget = DragDropTarget::new(hwnd, handler).into();
unsafe { RegisterDragDrop(hwnd, &drag_drop_target) }.is_ok()
```

`DragDropTarget` 实现的 `IDropTarget` 只在数据含 `CF_HDROP`（文件列表）时把 `*pdwEffect` 设为 `DROPEFFECT_COPY`，否则 `DROPEFFECT_NONE`。

**为什么这会打死页内拖拽**：

1. Win32 的 `RegisterDragDrop` 对一个 HWND **只能注册一个** `IDropTarget`（重复注册返回 `DRAGDROP_E_ALREADYREGISTERED`）。wry 是**顶掉 WebView2 自己的那个**。
2. Chromium 的页内 HTML5 拖拽**并非纯 DOM 事件** —— 它会走出去调用 OS 的 `DoDragDrop` 拖拽循环，再由光标下 HWND 的 `IDropTarget` 回灌。
3. 既然回灌口被换成「只认 `CF_HDROP`」的实现，页内那次拖拽的数据（非 `CF_HDROP`）就被判 `DROPEFFECT_NONE`：`dragover` 永远到不了 DOM、无从 `preventDefault()`、光标恒为 🚫、`drop` 不触发。

官方措辞（`tauri_utils::config::WindowConfig::drag_drop_enabled`）：

> 「**Disabling it is required to use HTML5 drag and drop on the frontend on Windows.**」

[tauri#15138](https://github.com/tauri-apps/tauri/issues/15138)（标题就是 "Windows: dragDropEnabled: true blocks HTML5 dragover events (Forbidden 🚫 cursor Paradox)"）请求「hybrid 模式：原生管外部文件 + HTML5 事件仍到 webview」，**被 closed as not planned**。

**➜ 两个参考项目的配置差异，正是这个约束的必然结果**：note-gen 有 drag-handle 所以必须 `false`；TMD 没有所以可以留 `true`。

## `@tiptap/extension-drag-handle` 是纯 HTML5 DnD

对 `3.19.0` 的 dist 做词频统计：

| 关键字 | 出现次数 |
|---|---|
| `draggable` / `dragstart` / `dragend` | 3 / 3 / 3 |
| `dataTransfer` / `setDragImage` | 3 / 1 |
| `view.dragging` | 1 |
| **`pointerdown` / `pointermove` / `pointerup` / `mousedown`** | **0 / 0 / 0 / 0** |

实际代码：

```js
element.draggable = true;
element.addEventListener("dragstart", onDragStart);
event.dataTransfer.setDragImage(wrapper, 0, 0);
view.dragging = { slice, move: true };   // 交棒给 ProseMirror 的 HTML5 DnD 节点移动
```

**零 pointer/mouse 事件，没有任何后备路径。** 与 `dragDropEnabled: true` 是硬冲突，无法绕过。

## 决策

**`dragDropEnabled: false`。保住 (a) 与 (b)，牺牲 (c) 的真实路径。**

| | 实现 | 结果 |
|---|---|---|
| **(a)** 块把手 | `DragHandle` + `NodeRange`（必装 peer） | ✅ 保住 |
| **(b)** tab 排序 | **dnd-kit（PointerSensor）** | ✅ 保住，且与 `dragDropEnabled` 取值无关 |
| **(c)** 拖文件入窗 | 降级为 P2，见下 | ⚠️ 牺牲真实路径 |

### dnd-kit 不受影响 —— 已实测确认

对 `@dnd-kit/core@6.3.1` 的 dist 做词频统计：

| 关键字 | 次数 |
|---|---|
| **`dataTransfer`** | **0** |
| **`setDragImage`** | **0** |
| `pointermove` / `pointerup` | 1 / 1 |
| `PointerSensor` / `MouseSensor` / `TouchSensor` / `KeyboardSensor` | 8 / 3 / 3 / 4 |

`dataTransfer` 与 `setDragImage` **双零**是决定性证据 —— 任何走 HTML5 DnD 的实现都不可能不碰 `dataTransfer`。

> ⚠️ 因此 **`react-dnd` 的 `HTML5Backend` 被明确禁用**（FR-604 / FR-711 已写进需求）。它会和 `true` 冲突，也和我们的架构假设不符。

### (c) 的降级方案

真实路径拿不到，因为：

- Chromium/WebView2 的 `File` 对象**没有** `path` 属性（那是 Electron 的私有扩展）
- **Tauri v2 唯一能拿到真实磁盘路径的入口就是原生 `DragDropEvent::Drop { paths }`** —— 正是被 `false` 关掉的那个
- 无任何官方 API 能把 HTML5 drop 的 `File` 映射回路径（`@tauri-apps/plugin-fs` 没有，`window.__TAURI__` 下也没有）

降级行为：HTML5 `drop` 读 `dataTransfer.files`，用 `file.text()` 拿内容 + `file.name` 拿文件名，以「未命名文档」新建 tab，保存走另存为。

**这个降级依赖一个未验证的前提**：#15138 报告者称 `false` 下外部文件的 `e.dataTransfer` 本身就 "blocked/empty"。若为真，则 (c) 彻底归零。

**➜ 这是整个项目唯一必须动手实测的技术点，约 1 小时，已列为 [路线图](../09-开发路线图.md) 阶段 0 的第一项，且有明确的两个分支。**

### (c) 的替代路径（都不受本冲突影响）

用户原始需求「从系统文件管理器中的文件用 NoteBoard 打开」由这四条覆盖，**(c) 从来不是用户点名要的**：

| 路径 | 需求 | 状态 |
|---|---|---|
| 双击文件关联 | FR-101 | NSIS 自动写 ProgID，开箱可用 |
| 右键 → 打开方式 | FR-102 | 需 `installerHooks` 手写 `OpenWithProgids` |
| 拖文件到 exe / 任务栏图标 | FR-103 | 走 argv，与窗口拖放无关 |
| 应用内打开对话框 | FR-105 | `tauri-plugin-dialog`，能拿到真实路径 |

## 被否方案

### `dragDropEnabled: true`，放弃块把手

否决：块把手是用户**主动追加**的需求（在被问「Markdown 渲染增强要哪几项」时自己补的「像 NoteGen 一样的行前八个点拖动排序」）。而 (c) 是我在写需求时自己加的 P1，用户原话里没有。**用户明确要的赢过我自己加的。**

### 运行时切换 `dragDropEnabled`

不可行：[tauri#13189](https://github.com/tauri-apps/tauri/issues/13189)「toggle dragDropEnabled at runtime」至今 OPEN。`disable_drag_drop_handler()` 是建窗时一次性的。

### 按窗口拆分（编辑窗口 `false`，另一个窗口 `true`）

技术上可行（`dragDropEnabled` 是每窗口字段），但 (a) 和 (c) 都发生在**同一个编辑器窗口**，拆分解决不了本冲突。

### 另开一个透明 webview 专收拖放

否决：需要 `unstable` feature 的多 webview（`Window::add_child` + `WebviewBuilder`），而且：

1. `unstable` 无 semver 保障
2. [tauri#13466](https://github.com/tauri-apps/tauri/issues/13466)：Windows 上 Alt+Tab 回来 webview 拿不到焦点，修复在**未发布的 2.12.0**
3. 覆盖在编辑区上的 webview 会吞掉鼠标

### 自己实现 pointer-events 版的块把手

未否决，但排在后面。若将来 (c) 变成刚需，这是唯一能同时保住三者的路：绕过 `@tiptap/extension-drag-handle`，用 pointer 事件 + 手动调 ProseMirror 的 `replaceStep` 移动节点。估工 3–5 天，且要自己处理拖拽预览与落点指示。**不在首版范围。**

## 代价

1. **无法把文件拖进窗口打开（真实路径）。** 用户要用另外四条路径之一。
2. **降级方案本身也可能不可用**（取决于阶段 0 的实测结果）。若不可用，FR-104 整条取消。
3. **锁死了 `dragDropEnabled: false`** —— 将来任何需要原生文件拖放的功能（比如拖图片进编辑器插图，FR-313 的拖入部分）都受同一约束。这也是 FR-313 的拖入被降为 P2 的原因。
4. 所有 DnD 实现都必须走 pointer 事件路线，团队要知道这条纪律，否则有人装了 `react-dnd` 就会踩坑。**已写进需求条文本身**（FR-604 / FR-711 明文禁止 `HTML5Backend`）。

## 什么情况下该重新考虑

- Tauri 实现了 hybrid 模式（目前 closed as not planned）
- 拖文件入窗被证明是高频刚需 → 那时走「自己实现 pointer-events 版块把手」这条路
