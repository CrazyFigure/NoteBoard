# ADR-011：持久化方案

**状态**：✅ 已定
**日期**：2026-08-17

---

## 背景

note-gen 用 **SQLite**（`tauri-plugin-sql` + `sqlx 0.8.6`，feature `sqlite`），全部 DDL 在前端 TS 侧执行，Rust 无 migration。它存了：

- 画布（表 `canvases`：`content` 存整份 JSON，`undoStack`/`redoStack` 各存最近 50 快照，`thumbnailPath`，软删除 `deletedAt`）
- 笔记索引、向量、标签、AI 会话等

另有 `tauri-plugin-store`（`store.json`）存设置与 tab 状态。

NoteBoard 需要持久化的东西列全了只有这些：

| 内容 | 量级 | 变更频率 |
|---|---|---|
| 主题与排版设置 | < 2 KB | 低 |
| 面板宽度与折叠状态（按窗口） | < 1 KB × 窗口数 | 中 |
| 窗口位置尺寸 | 插件托管 | 中 |
| 会话快照（窗口 + tab 列表） | < 20 KB | 退出时一次 |
| 草稿（未保存内容的崩溃保护副本） | 与文档等大 | 周期性 |
| 最近打开列表 | < 5 KB | 低 |

**画板不需要数据库** —— 见 [ADR-008](ADR-008-画板引擎与文件格式.md)，一个画板就是一个 `.excalidraw` 文件，躺在用户目录里。

## 决策

**不使用 SQLite。全部用 JSON 文件，放在 `%APPDATA%\NoteBoard\` 下。**

```
%APPDATA%\NoteBoard\
├── settings.json          主题 + 排版 + 编辑器偏好 + 文件偏好（含 revision 单调递增）
├── session.json           会话快照：窗口列表 + 每窗口的 tab 列表与布局
├── recent.json            最近打开的文件与目录（各上限 30 条）
├── window-state.json      由 tauri-plugin-window-state 托管，不手动碰
└── drafts\
    └── {sha256(docKey)}.json    草稿：{ key, content, savedAt, kind }
```

### 写入策略

| 文件 | 时机 | 方式 |
|---|---|---|
| `settings.json` | 每次设置变更（即时生效，FR-1302） | 原子写 + 广播 `nb://settings-changed` |
| `session.json` | 每个窗口关闭前 + 应用退出前 | 原子写 |
| `recent.json` | 打开文件/目录时，300ms 防抖 | 原子写 |
| `drafts/*.json` | 脏文档每 10 秒 + 失焦时 | 原子写；正常保存后**删除** |

**所有写入走与文档相同的原子写路径**（同目录临时文件 + rename）。配置文件被写坏会导致启动失败，这个代价比文档丢失更难排查。

### 读取容错

启动时任一 JSON 解析失败 → **不阻断启动**：

1. 把损坏文件重命名为 `{name}.corrupt-{timestamp}.json` 保留证据
2. 用默认值继续
3. 在设置页「关于」标记一次告警

**绝不因为配置文件损坏而打不开应用。**

### 草稿（崩溃恢复，NFR-302）

```
脏文档 ──每 10s / 失焦──► drafts/{sha256(key)}.json
                              │
正常保存成功 ────────────────► 删除该草稿
                              │
下次启动 ──► 扫 drafts/ ──► 非空？──► 「上次异常退出，有 N 个未保存的文件」
                                        └─► 逐个：查看差异 / 恢复 / 丢弃
```

用 `sha256(docKey)` 做文件名，避免路径中的非法字符与长度限制问题。

## 被否方案

### SQLite（note-gen 的选择）

否决理由：

1. **数据量与查询复杂度都不需要它。** 全部数据加起来 < 100 KB，没有任何需要 SQL 查询、索引、事务的场景。
2. **note-gen 需要它是因为 AI**（向量检索、笔记索引、会话历史）。我们不做 AI（[ADR-013](ADR-013-范围边界.md)），这个理由不存在。
3. **画板存数据库与「文件优先」定位冲突。** 用户必须能把笔记目录整体拷走。
4. **引入 migration 负担。** note-gen 的 DDL 在前端执行、Rust 无 migration，这个模式在多窗口下有并发写风险，且版本升级时的 schema 演进要自己写。
5. **增加约 2 MB 打包体积**（sqlx + sqlite），与 NFR-110（≤ 30 MB）的预算冲突。

### `tauri-plugin-store`

否决（部分）：它提供的就是 JSON 键值存储，功能上够用。但：

- 它的写入不保证原子性（我们要 NFR-305 的原子写）
- 多窗口并发写同一 store 的行为需要验证
- 我们只需要 5 个文件的读写，自己在 Rust 侧写 30 行更可控

**`tauri-plugin-window-state` 保留** —— 它托管窗口位置尺寸这件事做得很好，且不与我们的文件冲突。

### 把设置存在注册表

否决：不便于用户备份/迁移；卸载残留；无法手工编辑排查问题。

### 草稿存在文档同目录（如 `.a.md.swp`）

否决：会污染用户目录，且资源管理器里会看到奇怪文件（即使隐藏了点文件）。集中放 `%APPDATA%` 更干净。

## 代价

1. **无事务。** 多个文件之间没有一致性保证（比如 `session.json` 写成功但 `settings.json` 失败）。
   - 影响可接受：这些文件语义独立，不存在跨文件不变式。
2. **无并发控制。** 多窗口同时写 `settings.json` 理论上可能相互覆盖。
   - 对策：**设置的写入只允许通过 Rust 的 `save_settings` 命令**，Rust 侧持 `Mutex` 串行化。前端不直接写文件。
3. **草稿会占磁盘。** 一个 10MB 的脏文档就有一份 10MB 草稿。
   - 对策：草稿只对**脏**文档生成，正常保存后立即删；启动时清理超过 7 天的孤儿草稿。
4. **无法做「历史版本」功能**（那确实适合数据库）。不在首版范围。

## 什么情况下该重新考虑

- 引入本地版本历史 / 时间机器功能
- 需要全文检索（那时 SQLite FTS5 是正确选择）
- 数据量增长到 JSON 全量读写成为瓶颈（当前量级下不可能）
