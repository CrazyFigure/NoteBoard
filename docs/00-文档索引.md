## 三条实现红线

写代码时最容易踩、且后果最严重的三条。**已分别写进对应模块的文件头注释。**

### 红线 1：建窗必须切线程

```rust
// 🔴 WebviewWindowBuilder::build() 在同步 command 或事件回调中调用
//    会在 Windows 上死锁（wry#583）。必须 async fn 或 std::thread::spawn。
//    single-instance 回调尤其危险 —— 它运行在 WM_COPYDATA 同步窗口过程里。
```

### 红线 2：`emit` 在 v2 里是广播

```rust
// 🔴 Tauri v2 中，在 Window / WebviewWindow 实例上调 .emit() 也是【广播】，
//    与 v1 语义相反。定向必须显式 emit_to(label, ...)。
//    code review 必查：每个 .emit( 调用都要确认广播是故意的。
```

### 红线 3：`dragDropEnabled` 锁死为 `false`

```jsonc
// 🔴 改成 true 会静默破坏 TipTap 块把手（FR-311）。
//    wry 在 Windows 上顶掉了 WebView2 的 IDropTarget，
//    而 Win32 一个 HWND 只能注册一个 → 与页内 HTML5 拖拽硬冲突。
//    所有 DnD 必须走 pointer 事件（dnd-kit PointerSensor），禁用 react-dnd 的 HTML5Backend。
```

## 技术验证结论

> 阶段 0 完成后回填此表。**这是文档与现实对齐的锚点。**

| # | 验证项 | 结论 | 日期 |
|---|---|---|---|
| A | `dragDropEnabled: false` 下 `dataTransfer.files` 是否可用 | ⬜ 待验证 | — |
| B | Windows 建窗死锁（含对照组复现） | ⬜ 待验证 | — |
| C | 文件关联 + 单实例链路；NSIS hook 可用变量 | ⬜ 待验证 | — |
| D | 图标资产是否满足 Tauri 要求 | ✅ **已验证并处理**，见下 | 2026-08-17 |

### D 的详细结论

**已完成**：`src-tauri/icons/` 已从 `logo.ico` 生成全套（`icon.ico` 图层顺序 `[32,16,24,48,64,128,256]`，32px 在首位，六个必需尺寸齐全，alpha 通道完整）。可直接用于构建。

**发现的三个事实**（实现阶段需知道）：

| # | 事实 | 说明 |
|---|---|---|
| 1 | **`logo.ico` 才是真源，`logo.png` 不是** | `logo.png` 是 8-bit **RGB 无 alpha**（压白底导出版）。直接喂给 `tauri icon` 会得到白底方块图标。`logo.ico` 的七个图层 alpha 完整（256 层：78.1% 全透明 / 10.2% 全不透明 / 11.8% 半透明） |
| 2 | **原 `logo.ico` 的图层顺序不合规** | 首项是 16x16，而 Tauri 要求 **32px 排第一**。已在生成时修正 |
| 3 | ⚠️ **logo 的文档内页是透明的，不是白色** | 在深色背景（Win11 深色任务栏、墨夜主题 `#0f172a`）下，深色的文字线条与笔身几乎不可见，图标读起来像一个空框。**这是设计层面的问题，不是格式问题**，留待实现阶段按需处理 |

**关于第 3 点的可选处理方式**（供实现者参考，未执行）：

- 洞填充：以画布四角为种子对 alpha 做泛洪标记「外部」，剩余被框体包围的透明区域即纸面，填白 → 图标在任何背景上表现一致
- 或提供两套：亮色系统用透明内页版，深色系统用白内页版（Windows 不支持按主题切换应用图标，故实际意义有限）
- 或不处理：亮色背景下观感良好，深色下打折

> ⚠️ `logo.png` 与 `logo.ico` **几何不对齐**（同为 256 归一化后，png 非白内容 bbox `(63,47,209,208)` vs ico 不透明 bbox `(25,15,231,241)`），是两次不同尺度的导出，**不能机械合并两者的 RGB 与 alpha**。

## 参考项目调研结论

两个参考项目都做了源码级调研，结论已分散进各文档。此处只留**最反直觉的几条**，避免有人凭印象行事。

### codexu/note-gen

| 事实 | 影响 |
|---|---|
| **GPL-3.0-only**，无 classpath exception | 决定了 NoteBoard 的协议选择 |
| 编辑器是 **TipTap 3 + CodeMirror 6**，不是 Vditor | 决定了编辑器内核选型 |
| 严格二选一切换，**无分栏预览、无即时渲染**（grep 零命中） | [OUT-109](01-需求规格说明.md) |
| **没有真正的按语言高亮** —— 37 种扩展名全路由到 Markdown 编辑器，CM6 只装了 `lang-markdown` | **负面参考。** 我们必须比它多做 |
| 画板是 **React Flow 结构化节点图**，不是自由白板；默认存 SQLite，不是文件 | 我们改用 Excalidraw + 文件 |
| **没有多窗口**（`app.windows` 只有一个 `main`，无 `WindowBuilder`）；tab 拖拽 `handleDragEnd` 是空实现 | 多窗口这块零参考价值 |
| tab 状态存全局 `store.json` 单例 | **必须从一开始就改成 per-window**，越晚改越贵 |
| 排版四项**全部支持**，但机制各不相同（Tailwind 类名 / CSS 变量 / 直改 DOM style） | 我们统一用 CSS 变量 |
| 四层大文档机制的魔法值（`rootMargin: 800px`、`±2000 position`、`overscan: 2`、`24000/64000`、`20000`、`5000`、LRU 200） | **照抄不改**，但注明是经验值 |
| `dragDropEnabled: **false**` | 与它有 drag-handle 一致，印证了 ADR-014 的判定 |

### KoniKee/TMD_Type-Markdown

| 事实 | 影响 |
|---|---|
| **MIT** 协议 | 可直接复用配色 CSS（单向兼容 GPL） |
| 是独立桌面应用（React + Vite + Tauri + Vditor + Zustand），不是主题包 | 它的 Tauri 侧配置是可对照的生产实现 |
| 8 套主题，**晨光与琥珀都是亮色，都无暗色孪生变体** | 深色主题用它的 `mo-ye`（墨夜） |
| **晨光与琥珀都没定义 `--hljs-*`**（源码注释「亮色使用默认hljs，无需定义」），走 GitHub 冷调回退 | 琥珀的暖调高亮必须我们自研 |
| 22 个 `--hljs-*` 变量中 **7 个是死变量**（定义了从未被消费） | 我们只定义 17 个有效的 |
| `.hljs-addition` 挂 keyword（红）、`.hljs-deletion` 回退绿 —— **语义是反的** | 修正 |
| 墨夜的 `--editor-accent`（`#60a5fa`）与 `--accent-500`（`#3b82f6`）**不一致** | 统一为 `#60a5fa` |
| 表格斑马纹**实际不存在**（被自己的 `!important` 覆盖失效） | 我们主动不写斑马纹 |
| **字体族与字号不可调**（沿用 Vditor 自带） | FR-1101/1102 要我们新做 |
| Vditor 自托管 **528 个文件手工提交进仓库**，无同步脚本 | 换 TipTap 的理由之一 |
| `dragDropEnabled: **true**` | 与它没有 drag-handle 一致，印证 ADR-014 |
| `devUrl` 是 `1420` 但 vite `server.port` 是 `3000` —— 配置不一致 | 我们两处必须一致 + `strictPort: true` |

## 文档维护规则

| 规则 | 说明 |
|---|---|
| **需求编号永不复用** | 废弃的需求保留编号并标注「已废弃」（如 FR-613），不删除 |
| **ADR 定稿后不改正文** | 要改就新开一份，把旧的状态改为「已被 ADR-xxx 取代」 |
| **术语表先行** | 发现新概念先加进[术语表](02-术语表.md) 再写代码 |
