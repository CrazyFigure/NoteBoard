# P0 修复报告：真机内存持续增长（4GB）与新建 MD 首次不显示

修复日期：2026-09-07。依据用户真机反馈（打开三个小文件内存升至 4GB；新建 MD 后须切走再切回才能打开）完成定位与修复。本文覆盖泄漏根因的完整定位链、修复方案、修复前后对比验证与仍未完成项。

**结论：内存泄漏根因为 VisualKernel 传入 TipTap 扩展 options 的组件闭包经 V8 Context 共享持有整个 editor 圈（模块级 ResolveCache → NodeType → extension options → 组件 Context → editor），每次切换/回收重建泄漏一个完整 editor+schema+扩展对象。修复后（模块级工厂 + emitter 解耦）：120 次切换对象泄漏归零（240 个被驱逐 editor 全部回收；修复前 240/240 永久存活）、heap 增速由线性 +18.1MB 收敛为趋平 +6.6MB。新建 MD 在隔离真实浏览器（真实扩展集+StrictMode+真实 newMarkdown）复测正常（1.8s 内可编辑，无需切换）——用户症状判定为内存泄漏（4GB 下 GC 压力卡慢）的次生表现；另补齐新建路径的编辑器资源预取。**

### 根因机制（heap snapshot 保留路径 + V8 Context 语义）

heap snapshot（42MB）反向解析出的 Editor 保留路径：`模块级根 → SourceTextModule → ... → ResolveCache(prosemirror-view 模块级解析缓存) → _ResolvedPos → _Node(文档节点) → _NodeType → 扩展闭包链 → Editor`。

完整机制：
1. **prosemirror-view 的模块级 `ResolveCache`** 强持有最近 resolve 的文档节点（`Node.resolve()` 缓存）——`_Node → _NodeType → extension spec/options` 是模块级根可达的常驻链。
2. **LinkClickHandler 的 options 处于该链上**（扩展经 TipTap 的 schema 构建挂入 NodeType）。
3. **V8 的闭包 Context 共享**：同一函数作用域（组件函数体）创建的所有闭包共享一个 Context 对象——`onOpenLinkModal` 闭包（哪怕只引用 `docKey` 字符串）与 `handleOpenLinkModal`（`useCallback`，捕获 `editor`）共享 Context，该 Context 的变量槽持有 editor。
4. 合并：**模块级 ResolveCache → NodeType → LinkClickHandler options.onOpenLinkModal 闭包 → 组件共享 Context → editor（完整圈：editor+schema+全部扩展+文档）**——每个被销毁的 editor 都从模块级根可达，永不回收。
5. 每次切换/回收重建泄漏一个完整圈（实测约 150KB/次，dev 未压缩环境更大）——用户频繁切换（叠加"新建不显示"迫使用户反复切换）→ 4GB。

**为何实验 I（emit 版）仍泄漏**：闭包创建于组件函数体内即共享组件 Context——与捕获什么无关（V8 按作用域共享，不按引用裁剪到零）。

### 修复（`VisualKernel.tsx`）

`onOpenLinkModal` 改为**模块级工厂** `makeLinkModalOpener(docKey)` 创建（工厂闭包只捕获参数作用域，与组件 Context 无关），经 `emit('open-link-modal', { key: docKey })` 触发组件内已有的 `on('open-link-modal')` 监听（按 docKey 过滤 → `handleOpenLinkModal`，组件内闭包可安全捕获 editor——不处于 NodeType 链上）。原 `openLinkModalRef` 桥接删除。源码处含完整中文注释说明禁令：**禁止向 extension options 传入组件内创建的闭包**。

## P0-1 新建 MD 首次不显示：定位与处置

**隔离复现尝试（三层层级）**：
1. 协调器级（真实 TipTapEditor + 新建数据形态：untitled key、content=''、viewMode=null）：通过（挂载即可输入）——`test/startup/newDocumentFirstRender.test.tsx` 2 例。
2. AppShell 级（真实顺序：空壳渲染 → 点击新建 → 真实 EditorHost/TipTapEditor）：通过——`test/startup/newDocumentAppShell.test.tsx` 1 例（首次尝试失败系测试 mock 共享扩展实例的假差异，已修正为与真实 buildExtensions 一致的每次新实例）。
3. 隔离真实浏览器（真实扩展全量 + StrictMode + 真实 `newMarkdown`）：**通过**——新建后 1.5s（修复后 1.8s，首开含模块加载）即可编辑，静置 6s 零加载提示、无错误、contenteditable 在 DOM。

**判定**：前端组件链无法复现"新建后须切换才能打开"。结合用户同时在 4GB 泄漏会话中操作——**判定该症状为内存泄漏的次生表现**（4GB 下 GC 压力极大，模块加载/首次渲染被拖慢到看似"打不开"；切走再回来时资源已缓存所以"能打开"）。**P0-2 修复后预期自愈**——此判定待用户真机确认（见"仍未完成项"）。

**防御性改进**（`welcomeActions.ts`）：新建文档路径补齐 `prefetchEditor`（与 openDocument 打开路径一致）——首次新建不再从零加载模块（fallback 期缩短；资源与渲染共享注册表，预取后直接命中 fulfilled 状态）。

## P0-1 追加修复（2026-09-07 第八轮：用户复测反馈"仍一直显示正在加载，切走再切回才好；1.8s 太慢"）

上一轮隔离复现未果后，本轮以测试驱动抓到**机制级根因**并根治：

**根因（测试实证）**：`EditorHost` 此前经 **React.lazy** 渲染编辑器——lazy 的 ctor 即便返回**已 resolve 的 promise**，首次渲染仍要走 pending→微任务→retry 链：**本次渲染必 suspend、fallback 必提交一次**。慢环境（dev 冷启动、真机）下这段 fallback 期被放大为"一直显示正在加载编辑器"；用户切走再切回触发重渲染时资源已 ready 才"显示好"。（`newDocumentAppShell` 的零 fallback 断言复现：ready 后挂载 fallback 计数仍 +2。）

**修复（三层）**：
1. **EditorHost 渲染路径重做**：弃用 React.lazy/Suspense——`useSyncExternalStore` 订阅资源状态（`subscribeEditorResource`/`getEditorResourceSnapshot`，快照引用稳定）：**ready 时同步渲染缓存组件（零 fallback 提交）**；loading 渲染加载占位；error 渲染错误视图（含安全重试——`retryEditorLoad` 重建条目并通知订阅者自动重渲染，比 lazy 的 rejection 缓存可靠）。重试链全程有重渲染保障，不依赖微任务 retry。
2. **欢迎页空闲预取**（`WelcomeScreen`）：首帧后 `requestIdleCallback`（jsdom 回退 setTimeout）预取 markdown+code 资源——用户看到"新建 Markdown"卡片即预取意图信号；点击时资源已 ready。
3. **keep 登记 bug**（`editorSuspension.ts`）：`suspendEditorInstance` 的 capabilities=null 分支（lazy 加载中的标签）keep 命中时未设置 `keepAliveKey`——切走时"加载中的新建标签"被误逐出渲染集合（切回时重挂载、再次显示 fallback）。keep 分支统一登记。

**验证（隔离真实浏览器，真实扩展集+StrictMode+真实 newMarkdown）**：
- 预取完成后点击新建：**100ms 可编辑、零 fallback、无错误**（目标 <1s 达成，余量 10 倍）。
- 页面就绪立即点击（预取并行中）：**100ms 可编辑**，loading 占位在资源 ready 时自动退出（useSyncExternalStore 重渲染链）。
- 正式测试：`newDocumentAppShell` 新增"预取后新建零 fallback"断言（263ms 完成）；一轮 retry 反例按新接口适配（行为断言不变：失败→重试→恢复）。
