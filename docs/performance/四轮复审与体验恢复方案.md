## R4-01 · 首要体验问题：切换与回收绑定，连仍保留的编辑器也做全文工作

位置：[AppShell.tsx:296](C:/Software/WorkSpace/NoteBoard/src/components/AppShell.tsx:296)、[editorSuspension.ts:59](C:/Software/WorkSpace/NoteBoard/src/features/session/editorSuspension.ts:59)、[Markdown 能力实现](C:/Software/WorkSpace/NoteBoard/src/features/editor-md/editorCapabilities.ts)。

当前每次 activeKey 变化都枚举全部后台已挂载项，逐项 await suspendEditorInstance。每项先 flush，再更新 keepAliveKey；最后才决定谁真正卸载。Markdown 没有 pending 时的 flush 仍会调用 serializeMarkdown。

**D03 已复现：**两个未编辑、始终保持挂载的热标签 A/B 往返，仍发生 `flush(B)、flush(A)`。此时没有任何实例需要卸载。用户仅切个标签，也被收取全文序列化的成本；文档越复杂，这条路径越不合适。

真实浏览器另外确认：打开四个短 MD，再回到 A，A 正文仍在 store，但内核和能力已经不存在，页面出现“正在加载「A.md」的编辑器…”。这属于前端回收与重建链，不能统一归因于 Tauri 冷启动。

必须调整的实现结构：

1. **激活与回收分离。**激活已有热实例只更新可见性、焦点和必要视图度量；先展示目标内容，不在激活链中对其他文档逐一全文序列化。
2. **先选定真正需要回收的对象，再执行它们的交付屏障。**最终会留下的实例，不应为了“回收准备”反复导出全文。相同 revision 已可靠同步时复用已有证明，但不能跳过未提交输入。
3. 回收任务有 session/instance/调度批次身份，可取消、可合并；任务返回时检查用户是否已重新激活该文档。不要让快速 A→B→A 的旧任务决定新活动实例的命运。
4. 保留用户未确认的策略参数为空白：具体保活数量、内存阈值、空闲时间等，按后文流程提交用户确认。不得换一个未经确认的固定数字继续实施。

验收首先检查“热命中”路径：内核身份不变、无文件重读、无模块重装载、无对未变化文档的全文 flush、不显示加载页；同时保证最近输入、撤销、选区和滚动不丢。哪些文档应保持热状态，由用户确认的缓存策略决定。

### 必须给用户确认的缓存方案

以下是候选方向，**本报告不选择、不批准任何一个，也不填写默认容量/时间阈值**：

| 候选方向 | 切换影响 | 内存影响 | 实施前需给出的数据 |
| --- | --- | --- | --- |
| 常用工作集保活，预算不足才回收较冷文档 | 常用命中快；超出工作集后仍可能冷恢复 | 高于只保留两个实例，需要真正可执行的预算 | 各类型单实例成本、工作集命中率、冷恢复成本、不同预算曲线 |

### 让内存优化有真实收益

React 卸载实例不等于已经加载的 JS 模块、字体和所有缓存会从进程消失；正文、基线和撤销历史也有保留需求。频繁重建可能增加瞬时分配与垃圾回收压力，出现“切换更慢，但总内存并没有明显更低”。这一机制需要采样验证，不能仅靠猜测归因。

按固定样本记录：

- 空壳、单个短 MD、复杂 MD、source、每类重型编辑器；第一次打开与再次激活分开。
- 多文档往返时内核创建/销毁次数、模块加载 fallback 次数、parse/serialize 次数、主线程长任务。
- Tauri 及所属 WebView2 进程组的 Private Bytes/Working Set、JS heap 和模型/历史/字体/iframe 等保留引用；不要只看主 exe。
- 关闭同一路径与不同路径的循环，检查所有会话表、history adapter、pending、恢复快照、资源监听与定时器。
- 同一浏览器模块已加载、同一用户设置、相同字体包和文档集下对比候选策略；时间和内存同时报，不只报最好的一项。

测量得出候选参数后再请求用户确认。具体内存阈值不能在没有这些数据时拍定。
