## 反例修复明细

### D03 · 热标签往返触发不必要全文捕获（R4-01）✅

**根因**：每次 activeKey 变化，收敛批次对**全部**非活动挂载项逐个 `await suspendEditorInstance`（每项先 flush 再改保活）——两个都保留的热标签往返也各收一次全文序列化；且批次没有调度身份，快速 A→B→A 的旧批次迟到提交可能改写渲染集合。

**修复**（`editorSuspension.ts` + `AppShell.tsx` + `editorCapabilities.ts`）：
1. **激活与回收分离**：批次先确定**真正要驱逐的对象**（候选中除 previous 外的项——它们超出"活动 + 最近一个"的既有预算），只对驱逐项执行完整交付屏障（flush → 身份/revision 校验 → 视图捕获）；**最终保留的实例（previous）走轻量路径**——经新能力 `hasUnconfirmedInput()` 判定（J2 pending 未物化 / 镜像不同步 / 正文未知）为零时**跳过全文 flush**（内容已在镜像；flush 是幂等屏障，此时不执行它不丢内容）。有未确认输入时保守走完整屏障——不跳过未提交输入。
2. **keep 语义修正**：keep = **previous（刚切走的标签）**——用户最可能切回的最近使用项（此前实现读取的是上一批次的 keepAlive 残值，两次往返全部误判为"必须驱逐"）。往返切换时候选只有 previous，keep 命中 → 零全文 flush（D03 契约：flushLog === []）。
3. **批次调度身份**：`convergenceBatchIdRef` 单调递增；旧批次提交前校验身份——用户已再次切换（新批次启动）时不改写渲染集合（快速 A→B→A 的旧任务不决定新活动实例的命运）。

**验证**：D03（两个未编辑热标签往返 flushLog=[] 且 2 宿主保持挂载）转绿；隔离浏览器 24 次往返后 A/D 实例保留、B/C 回收，与预算一致。

**未动用户策略**：默认预算仍是"活动 + 最近一个"（现状保留，未擅自改动——缓存策略候选方案仍待用户确认，见"仍未完成项"）。

### D08 · 成功模块重挂载重新进入 Suspense（R4-02）✅

**根因**：`createLazyEditor` 每次调用返回**新的** React.lazy 对象；EditorHost 被（回收）卸载后重挂载创建新 lazy——底层 ES 模块已缓存不代表新 lazy 包装处于 fulfilled 状态，重挂载宿主重新提交"正在加载…的编辑器"fallback。

**修复**（`editorLoaders.ts` 模块级资源注册表）：按入口类型维护 `{ lazyComponent, promise, status: loading/ready/error, error }` 资源条目——缓存 loader Promise、成功组件与**稳定的 lazy 包装**（同一 Promise 引用，单次 import）；成功后所有宿主复用同一 fulfilled lazy，重挂载**不再进入加载边界**；`retryEditorLoad` 仅在 status=error 时丢弃缓存了 rejection 的旧包装重建（成功资源 retry 返回 false 不重建——不为重试机制让所有正常重挂载重新 suspend）；`prefetchEditor` 与渲染复用同一资源条目（预取完成后渲染直接命中 fulfilled）。EditorHost 的错误边界 key 含 tab.key 与 retryGeneration（跨文档切换也重置边界状态）。

**旧实现形态断言的修正说明**（复审第 84 行要求）：`test/startup/editorLoading.test.tsx` 原两例"每次 createLazyEditor 生成新实例"是**实现形态断言**——复审明确指出其不能作为产品验收标准（新实例正是 D08 的根因）。已改为行为断言：成功资源跨调用复用同一包装（ready 后复用不变、不同入口互不共享）；成功资源 retry 不重建、无条目 retry 安全返回；prefetch 与渲染共享同一条目。**行为前后差异**：旧行为=每次新包装（重挂载重新 suspend）；新行为=成功资源稳定复用（D08 反例的期望行为）。

### D02 · 大文档 + visual 标签模式进入无内核空白（R4-03）✅

**根因**：初始化中 `initialMode = tab.viewMode ?? (isLarge ? 'source' : 默认)`（大文档+visual 标签 → initialMode='visual'），大文档分支先设 source，随后**统一应用段**又按 initialMode 把 viewMode 设回 'visual'——既无 TipTap（大文档不挂载）又不创建 CodeMirror（source 条件不成立）→ 空白无内核。

**修复**（`TipTapEditor.tsx`）：引入 **resolvedMode 单次决策**——`requestedMode`（用户意图：标签 viewMode ?? 设置默认）与"大文档限制"合并为 `resolvedMode = isLarge ? 'source' : requestedMode`，初始化只应用一次（大文档分支与统一应用段使用同一值），分支间不再互相覆盖；历史初始化与 source 内核创建均按 resolvedMode。**不改变任何非大文档文件的默认模式**。

### D04/D05 · closing 永久泄漏 + 第二次关闭保护失效（R4-05）✅

**根因**：(1) 关闭事务完成后 closing 条目**永久保留**（"旧会话永久拒绝"的旧设计），活动表清理条件又要求无 closing——互相阻止，30 个路径关闭后两表各 30 项泄漏；(2) `beginClosing` 幂等为"有条目就不写"——同路径重开（新会话新代际）后的**第二次关闭**沿用第一次的旧关闭代际，`isClosing`（当前代际 ≤ 关闭代际）错误返回 false，迟到写入成功落盘。

**修复**（`documentSession.ts` + `windowStore.ts`）——closing 从"路径墓碑"改为**会话状态**：
1. `beginClosing` 总是记录**当前**代际（同代幂等；换代后的新关闭事务以新代际覆盖——第二次关闭同样阻止该会话的写任务）。
2. `isClosing` 判定改为"条目存在且当前代际 === 关闭代际"（代际推进=新会话恢复接纳；条目释放=事务完成）。
3. `disposeTabLifecycleAsync` 的 finally：**释放本事务代际的 closing 条目**（drain 期间重开且又开启新关闭时条目已被覆盖为新代际，不误清新事务），随后 `releaseSessionAfterClosing` 做孤立活动表回落。旧会话迟到写任务的作废由活动表 token 校验承担（`isSessionCurrent`——dispose 已推进/清除代际），不依赖墓碑。
4. `disposeTabLifecycleAsync` 作为公开独立入口时**补齐会话终结**（documents 移除 + 代际推进；经 closeTab 的同步清理路径幂等跳过）——第二次"关闭"（不经 closeTab 直接调用）同样终结会话。

**验证**：D04（30 路径真实 closeTab 后 active/closing/queue 全 0）与 D05（关-开-再关后 `writeDocumentWithBarrier` 返回 false 且 0 次写盘）均转绿。

### D06 · 另存为注销等待期间的 J2 pending 输入丢失（R4-06）✅

**根因**：上轮 C07 的"remove 前补读镜像"只覆盖**已进镜像**的输入；source/visual 模式新输入先进 J2 pending（500ms 防抖前镜像仍是旧值）——注销 await 期间暂存的 `typed-during-unregister` 不在镜像里，新会话最终内容仍是 base。

**修复**（`saveDocument.ts` 身份切换临界区）：`remove` 前显式**物化 pending**（`flushPendingSourceSnapshot` → `flushPendingVisualSnapshot`；会话代际校验由 flushPending 内部执行——migrate 推进后的代际与 pending 捕获一致），物化结果作为期间输入进入新会话最终内容；无 pending 时回退镜像补读（C07 语义保留）。

### D07 · Drawio 迟到回包被下一个请求接纳（R4-07）✅

**根因**：本地 requestId 只保护本地 timer/resolve 清理——export 回包**不携带请求 ID**（嵌入协议限制），事件处理器无条件把回包交给"当前 pending"：A 超时 → B 在途时，A 的旧 XML 被当成 B 的成功捕获。

**修复**（`DrawioEditor.tsx`）——协议关联手段核对结论：drawio 嵌入协议的 export 回包无原生请求标识，可靠性质只有"**每请求恰一个回包** + 引擎串行处理、回包按请求顺序到达"。据此实现**作废名额（zombie reply credits）**：请求超时作废时登记一个待收回包名额；之后到达的回包先消耗名额（判为旧请求的迟到回包，丢弃），名额耗尽后才交付当前在途请求。A 超时→B 在途时，A 的迟到回包先被名额吸收，B 不接纳；B 自己的回包到达时名额已耗尽、正常交付。无 pending 的迟到回包丢弃语义保留（C11）。

## R4-02 · "小文件一直显示正在加载编辑器"定位闭环（验收阻塞项）✅（隔离部分）／真机部分开放

**本轮执行**（完整记录：`test-results/performance/review-20260907-round4/browser-observations-after-fix.md`）：

   - **快速往返 24 次（60ms 间隔）后停在 A，不再点击、不派发激活事件**：静置 8 秒每 100ms 采样——**10/10 零可见加载提示、10/10 正文含完整内容、errors=[]**；A 实例（批次末重建）正文完整、D 保留（keep=previous）、B/C 回收（store 正文保留）。

## P0-2 内存泄漏：根因与修复

**定位方法**：隔离 Vite（独立端口/缓存，内存 IPC 替身）+ Chrome headless（`--enable-precise-memory-info --js-flags=--expose-gc`）+ CDP WebSocket 驱动；真实 AppShell/TipTap 全扩展/StrictMode；WeakRef 存活探测 + 主动 GC 的十组对照二分实验 + 42MB heap snapshot 反向解析保留路径。

**二分定位链**：

| 实验 | 场景 | 结果（GC 后存活/总数） |
| --- | --- | --- |
| A | AppShell 3 文档 120 次切换 | 240/240 存活，heap 30.3→48.4 MB 线性；DOM 恒定；close-all 后仍 240/240；isDestroyed=true（销毁已执行，对象仍被引用） |
| B | 绕过 AppShell 直接挂卸 TipTapEditor | 57/57 → 排除 AppShell 层 |
| C | 纯 useEditor + 真实扩展 | 0/60 → 排除 @tiptap/react 与扩展集 |

| H | `buildExtensions(docKey, {onOpenLinkModal: 组件闭包})` | **60/60**（不传则 0/60）→ 锁定 LinkClickHandler options 的组件闭包 |
| I | 闭包改 emit 解耦但仍创建于组件内 | 60/60 → **闭包捕获什么都泄漏（哪怕只引用字符串）** |
| J | 模块级工厂创建闭包 | **0/60** → 修复确认 |

**根因机制**（heap snapshot 保留路径实证）：① prosemirror-view 模块级 `ResolveCache` 强持有最近 resolve 的文档节点 → `_NodeType → extension spec/options` 是模块级根可达的常驻链；② LinkClickHandler 的 options 处于该链上；③ **V8 闭包 Context 共享**——组件函数体内创建的所有闭包共享一个 Context 对象（`onOpenLinkModal` 闭包哪怕只引用字符串，也与捕获 editor 的 `useCallback` 共享 Context，Context 变量槽持有 editor）；合并：**模块级 ResolveCache → NodeType → 扩展 options 闭包 → 组件共享 Context → editor 完整圈（editor+schema+全部扩展+文档）**——每个被销毁的 editor 从模块级根可达而永不回收，每次切换/回收重建泄漏约 150KB（dev 未压缩环境更大），频繁切换累积至 GB 级。

**修复**（`VisualKernel.tsx`）：`onOpenLinkModal` 改**模块级工厂** `makeLinkModalOpener(docKey)` 创建（工厂闭包只捕获参数作用域），经 `emit('open-link-modal', { key: docKey })` 触发组件内已有的 `on('open-link-modal')` 监听（按 docKey 过滤 → 组件内 handleOpenLinkModal——组件内闭包可安全捕获 editor，不处于 NodeType 链上）。原 `openLinkModalRef` 桥接删除。源码注释写明禁令：**禁止向 extension options 传入组件内创建的闭包**。

**修复前后对比**（端到端，AppShell 120 次切换 + 主动 GC 采样）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 被驱逐 editor 存活（GC 后） | 240/240 全泄漏 | 0-9 瞬时 / close-all 后 **0/240** |
| heap（GC 后） | 30.3→48.4 MB（每 20 次 +3MB 线性） | 30.2→36.8 MB（增速递减趋平） |
| 单独挂卸 VisualKernel | 60/60 存活 | **0/60** |

修复后残余趋平增长为运行时正常行为（订阅/历史/基线/模块缓存），WeakRef 归零佐证非对象泄漏。

# P0-1b 追加修复（第八轮：新建 MD"一直显示正在加载"根治 + 1s 达标）

日期：2026-09-07。依据用户复测反馈（新建 MD 仍一直显示"正在加载编辑器"、切走再切回才好；1.8s 太慢要求 1s 内）完成。

## 机制级根因（测试实证）

`EditorHost` 此前经 **React.lazy** 渲染编辑器——lazy 的 ctor **即便返回已 resolve 的 promise**，首次渲染仍要走 pending→微任务→retry 链：**本次渲染必 suspend、fallback 必提交一次**。慢环境（dev 冷启动/真机）下该 fallback 期被放大为"一直显示正在加载"；用户切走再切回触发重渲染时资源已 ready 才"显示好"。以"预取完成后新建零 fallback"断言复现（ready 后挂载 fallback 计数仍 +2）。

## 修复（三层）

1. **EditorHost 渲染路径重做**：弃用 React.lazy/Suspense——`useSyncExternalStore` 订阅资源状态（`subscribeEditorResource`/`getEditorResourceSnapshot`，快照引用稳定）：**ready 时同步渲染缓存组件（零 fallback 提交）**；loading 渲染加载占位（不进入 Suspense）；error 渲染错误视图（含安全重试——`retryEditorLoad` 重建条目并通知订阅者自动重渲染，不自动刷新/不销毁未保存内容/不记 ready）。重试链全程有重渲染保障，不依赖微任务 retry。
2. **欢迎页空闲预取**（`WelcomeScreen`）：首帧后 `requestIdleCallback`（jsdom 回退 setTimeout 300ms）预取 markdown+code——用户看到"新建 Markdown"卡片即预取意图信号；点击时资源已 ready。新建路径的 `prefetchEditor`（第七轮补）保留。
3. **keep 登记 bug**（`editorSuspension.ts`）：`suspendEditorInstance` 的 capabilities=null 分支（lazy 加载中的标签）keep 命中时未设置 `keepAliveKey`——切走时"加载中的新建标签"被误逐出渲染集合（切回时重挂载、再次显示 fallback）。keep 分支统一登记。
